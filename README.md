# Possible Pieces

A locally runnable procedural construction instrument. React, TypeScript, Vite, Three.js, React Three Fiber and Drei. No external services, accounts or model library.

## Run

Install Node.js 20.19+ (or 22.12+), then in this folder:

```sh
npm install
npm run dev
```

Open the printed localhost URL. `npm run build` creates `dist/`; `npm run preview` serves that build. `npm test` runs the automated geometry tests. A pnpm lockfile is also included for reproducible installation with `pnpm install --frozen-lockfile`.

## Use

Enter toothpick and connector quantities and press Generate. The viewport alone darkens and assembles a numbered connected graph, then becomes a physical object. Drag to orbit, scroll to zoom, right-drag to pan. Pause, skip, replay, switch construction/object view or reset the camera. Select a gallery alternative or regenerate a new collection. Export Design saves the selected graph, seed, millimeter lattice spacing and scores as JSON.

## Physical model

`src/engine/physical.ts` holds configurable dimensions, in millimeters. Rod length is 63.5; diameter 2; connector arm reach 8; outer arm radius 2.8; bore radius 1.15; insertion depth 5. Connector-center spacing is `rodLength + 2 × (armReach − insertionDepth) = 69.5 mm`. The exposed rod is 53.5 mm. The procedural connector has six orthogonal tubular arms, recessed insertion stops, rounded lips and a rounded center. Rods penetrate the bores rather than ending at arbitrary connector centers. All connectors share the same orientation in this prototype.

## Architecture

- `engine/generate.ts`: seeded weighted connected lattice growth; tree plus cycle closure; support-oriented rotations; canonical signatures; descriptor-based diverse selection.
- `engine/validate.ts`: exact counts, lattice positions, unique occupancy, unit axial edges, socket reuse and connectivity. On a unit cubic lattice, distinct unit axial segments cannot intersect internally or pass through another integer lattice vertex. Component radii are much smaller than lattice spacing.
- `engine/scoring.ts`: support convex hull, weighted center of mass, ground contacts, proportions and graph descriptors. These are heuristics, not structural certification.
- `engine/worker.ts`: bounded candidate search off the UI thread; newer requests terminate prior workers.
- `components/Connector.tsx`: shared procedural hollow six-socket geometry.
- `components/Viewer.tsx`: physical rods, construction dots/labels, orbit camera, shadows and camera orientation.
- `components/Thumbnail.tsx`: lightweight isometric SVG previews of the actual graph; the main viewer uses full 3D geometry.

The default search evaluates 650 attempts and selects up to nine unique designs, aiming for seven estimated freestanding and two experimental where the pool permits. For dense or small sets, fewer results may exist or be found. The UI reports this instead of filling slots with duplicates. A finite failed search is reported as search exhaustion, not proof of impossibility. Basic feasibility checks use connectivity and the cubic-lattice edge-isoperimetric upper bound; these are necessary, not sufficient. Max 100 connectors keeps prototype search/memory bounded.

The assembly sequence grows a connected tree before closing loops. It explains graph construction; it does not guarantee a physical insertion order. Some builds require temporary support. Actual friction, joint stiffness, material weights, ground contact deformation and strength are not simulated.

## Design

White page, orange component controls, isolated product illustrations and a neutral studio viewport. Only the viewport darkens during construction. Responsive two-column desktop and stacked mobile layout. No remote fonts or assets. The supplied briefs referenced images that were not included as image attachments; this implementation follows their written specifications.

## Freestanding and shape controls

Freestanding Only defaults on and filters every gallery candidate using the same stability assessment. Turning it off targets a seven/two freestanding/experimental mix when candidates permit. Desired Shape recognizes chair, table, bridge, tree, tower, arch, house, cube and staircase, plus tall, wide, narrow, low, symmetric, asymmetric, branching, dense, open, stepped and spiral modifiers. Unsupported words are reported; this is an extensible rule parser, not arbitrary language understanding. Procedural per-candidate occupancy fields guide lattice growth, and shape scores affect ranking. Shape prompts are visual approximations, not functional furniture. Small budgets retain exact counts and simplify the result; search exhaustion never silently relaxes freestanding filtering.

The assessed orientation is retained for shape objectives; unprompted candidates explore axial resting orientations. The renderer places the floor at the lowest downward socket tip. Ground support uses an eight-point approximation to each downward socket's circular contact rim. Equal connector masses and rods weighing 0.35 connector units yield the projected center of mass. Signed distance to the support hull must exceed the configurable `STABILITY.margin`; a continuous score accounts for clearance, footprint, height, cantilever, loops and leaf joints. Thresholds live in `engine/scoring.ts`. Narrow supports and cantilevers can pass, but friction, elastic buckling, joint rotation and stiffness are only approximated by geometric risk penalties. These estimates are not engineering verification.

`GenerationOptions` carries both counts, freestandingOnly, shapePrompt and seed through the worker. Regenerate reads the same controls and changes only the seed. Each design/export carries shapeSimilarity, stabilityScore and its experimental classification. The bounded seeded attempt count makes identical options reproducible.

## Model comparison

Run the same design brief against Claude Sonnet 5.5, Opus 5.5 and Fable 5.2, then check every answer with this project's own geometry and stability code.

1. Put your Anthropic API key in `.env.local` (gitignored) as `ANTHROPIC_API_KEY=...`, or export it in your shell.
2. Run a brief:

```sh
npm run compare -- briefs/bridge-6in.json
npm run compare -- briefs/bridge-6in.json --dry-run          # print prompts and a cost estimate, call nothing
npm run compare -- briefs/bridge-6in.json --models opus,fable --runs 3
npm run compare -- --prompt "Make me a chair" --max-connectors 20 --freestanding
```

3. Open the comparison page at `/compare/` (linked as **Model comparison** in the generator footer). It shows the brief, a scoreboard and a 3D viewer for each model's design. Pick a saved run from the menu, and click a model to watch its build.

A brief file holds the text sent to the models and the constraints the checker enforces: `maxConnectors`, `maxRods`, `gapMm` and `freestanding`. Every model gets the same system prompt (`systemPrompt()` in `src/engine/compare.ts`), the same effort (`--effort`, default `high`) and the same repair policy. If a design misses the brief, the checker's report goes back to the model for up to `--repairs` more turns (default 2). The table reports first-try and final results separately. Server-side refusal fallbacks are off, so a design is always credited to the model that produced it.

The gap check looks along x and z for the widest band of ground with no contact at any depth and contacts on both sides. Its clear width is `D × 69.5 − 2 × 2.8` mm, where D is the lattice distance across the band. Results are saved to `results/<brief id>/<timestamp>.json`, including the prompt, every turn, token usage and estimated cost at list prices. `npm run check` typechecks the app and the runner.

### Writing briefs on the page, and deploying

The comparison page has a **Write a brief** tab. It sends the brief to `POST /api/compare`, which runs the same code as the CLI (`scripts/compare-handler.ts`). Locally, `npm run dev` serves that endpoint and saves runs to `results/`. On Vercel it's a function (`api/compare.ts`, 300 s limit). Runs made there can't be written to the repo, so the browser that made them keeps them.

The deployed site is password-protected. `middleware.ts` asks for HTTP Basic auth on every page and on the API (any username, the password in `SITE_PASSWORD`), and the API function checks it again. With no `SITE_PASSWORD` set, the deployment refuses every request. Set both variables in the Vercel project, then redeploy:

```sh
vercel env add SITE_PASSWORD production
vercel env add ANTHROPIC_API_KEY production
vercel deploy --prod
```

## Variable-angle hubs (prototype)

`hubs/index.html` (open `/hubs/` on the dev server) and `npm run hubs` turn a shape into toothpicks plus one 3D-printed hub per joint. Each hub's bores point exactly along its sticks, and each bore's stop depth is chosen so one uncut stick spans the gap: hub spacing = stick length + both stop depths.

- Shapes come in two kinds. A **mesh** (the banana; later, a text-to-3D model's output) becomes a triangulated shell: farthest-point sampling and Lloyd iterations place evenly spaced hubs on the surface, and sticks join hubs whose surface regions touch. A **part list** (the chair; later, parts labeled by a vision or language model) becomes a frame: rods become chains, plates become grids, and touching ends fuse.
- Size is free. The shape is scaled so spans land inside the band one uncut stick can cover (68.5–87.5 mm with the defaults), then hubs slide along the surface to pull outliers in.
- A bore's minimum stop depth depends on how close its nearest neighbour bore is: s·sin(θ/2) ≥ bore radius + wall/2. Sticks closer than about 14° can't share a hub.
- `src/hubs/params.ts` holds the dimensions. The bore is 2.1 mm, measured from the 18-hole test connector. That differs from `PHYSICAL.socketRadius` used by the lattice app.
- The report lists sticks that need trimming or fall short (beyond a 1 mm tolerance), the smallest stick angle and size of each hub, and whether the frame would be rigid with free pin joints. It does not simulate friction, strength or print orientation; hubs need supports.
- `npm run hubs -- banana --sticks 60` writes `out/hubs/<shape>/` with one STL per hub, a print-plate STL, `design.json` and `report.txt`.

## Slot constructions (prototype)

`/slots/` is the SLOT KITS tab in the site's tab bar (`src/components/SiteTabs.tsx`, next to GENERATOR and MODEL COMPARISON) and has three tabs of its own: Kit gallery, Kit sheet and Panel generator. `src/slots.tsx` mounts the page; `src/slots/ui/` holds the tabs and the 3D build scene and cut sheet they share.

**Kit gallery** (the default). Three modes, no form buttons. **Describe it · Claude**: type a brief (or click an example) and Claude Opus 5.5 sets up the engine: the form to grow (a table, a tower, a random form inside a floor circle, a sculpture, a low spread, a compact cluster), whether it needs a top and what kind, the piece count, disc size and sheet. **Designed by Opus**: Claude Opus 5.5 places every piece itself (see below), so symmetry and repetition in the brief are built, not left to chance. **Random · solver only**: no API call; the solver grows random designs up from the floor inside a footprint circle you set. In both, piece count, size, sheet, fit and (for random) the footprint can be adjusted after. Only the Circular kit is shown; the other kits stay in the engine (`VISIBLE_KITS` in `src/slots/recipe.ts`), and recipes are held to the visible ones. Open one for a 3D build animation, numbered build steps, and laser files: an SVG cut sheet (red cut, blue engrave), a DXF (layers CUT in red and ENGRAVE in blue) and a printable HTML assembly guide. Line weights follow the laser lab's rules: cut lines are 0.072 pt in the SVG (0.0254 mm, since 1 SVG unit is 1 mm), and the DXF is R2000 so every vector and both layers can carry lineweight 0 (R12 has no lineweights). The DXF follows the documented minimum for R2000 (the nine tables, model and paper space blocks, the root dictionary); a test checks its structure, handles and owners, but it has not yet been opened in AutoCAD. Each piece is engraved with its number and a letter at each slit, which the build steps refer to.

- Kits (`src/slots/kits.ts`): **Circular**: a disc with 1 slit, 2 slits at 90°, 2 slits at 180°, 3 slits, a half disc whose two notches are the 180° disc's slits running along its flat edge (H), and a half disc with one slit from the middle of its curved edge toward the flat edge (H1; it ends a branch like the 1-slit disc, with its flat edge facing away). **Triangular**: triangles with 1, 2 or 3 midpoint slits and a pinwheel triangle. **Pinwheel**: pentagon, hexagon and decagon with one offset slit per edge.
- Slits are snug (sheet + clearance), so every joint is a 90° cross. Wider slits would admit other angles but then the joint can rock within them. Even snug, a slit joint only resists turning about its own slit line through contacts one sheet thickness apart, so under load it is a hinge (see *Braced joints* below).
- Joining slit i of P to slit j of Q puts Q's slit frame at translate(ℓP + ℓQ, 0, 0)·Rx(ψ)·Rz(π) in P's slit frame: same line, facing back, mouths ℓP + ℓQ apart, ψ = 90° or 270°.
- Designs grow as trees (`grow`): a piece is kept only if it overlaps nothing and its straight slide into place clears everything already built, so the growth order is a verified build order. Towers extend the newest piece, compact designs fill the oldest. The design is then stood on the convex-hull face that tips last (towers within 35° of their chain axis, spreads on their thinnest direction), and the full engine checks run: interference, intact pieces, an independent assembly plan, stands, and no piece that gravity can pull out. Only designs that pass reach the gallery; the page reports why the rest were rejected.

- Up to 30 pieces. Designs grow about a fifth over the target; once standing, end pieces the engine's hold test finds gravity would pull out are pruned (repeatedly), the design is stood up again, and the newest end pieces are trimmed to the count. So a card may show slightly fewer pieces than asked for.
- Engraving is placed to clear every cut: the piece number at the point farthest from all edges and slits, each slit's letter just past its end or beside it. A test checks every label box against every cut.
- Slits are cut sheet + fit wide. Enter measured sheet thickness, and put the laser's kerf allowance into Fit.

**One shape, one size.** A kit is one shape at one size; its pieces differ only in their slits, and every piece in a design (cover included) is the same size. Kits: Circular (your five disc pieces), Triangular (1, 2, 3 midpoint slits and a pinwheel triangle), and single-piece Pentagon, Hexagon and Decagon kits (one slit per edge, as in the interlocking polygon sets). Two half discs are never joined notch to notch: both cuts are shallow edge notches, so the joint barely engages and the lying half disc hangs off a line with its weight to one side.

**Designs that need propping.** Every design shown passes every check except, for some, standing. While fewer than a third of the set need support, a design that will not stand in its intended pose (a tower upright, a random design on the floor it grew from) is kept in that pose instead of being dropped, provided its only failed check is Stands; tables always stand. Cards mark them "needs support". Filters above the gallery sort the set by standing (stands / needs support) and shape (upright: at least as tall as wide / low).

**Random** aims at no shape. Each design draws its branching style (chains, bushes or a mix) along with every piece and slit, and grows up from a floor inside a circle on it whose diameter you set (2–8 piece sizes, 4 to start). The first piece stands on edge with one of its in-plane axes as up, picked at random; a piece is kept only if nothing of it reaches below that piece's lowest point and the smallest circle round the whole plan, wherever its centre lands, stays inside the limit (`grow` with a `Footprint`, `enclosingCircle` in `src/slots/poly2d.ts`). Growth that stalls in the circle stops early and may end a few pieces short. The design then stands on that floor if it is steady there (within 15°), else on its steadiest face, and the plan is measured again; anything past the circle is dropped. Height is free. Crowding many pieces into a tight circle yields few designs: about 22 pieces fit 4 piece sizes, 30 want 5.

**Covers and tables** (`src/slots/grids.ts`, `src/slots/covers.ts`). A cover is a flat piece with no slits that rests level on top where the brief needs a surface: always for the table form, and for any other form whose recipe asks for a top. A tree of slit joints folds under a load on top (see *Braced joints*), so a covered design is always a stacked grid of discs, as you would build one by hand; the form only steers the grid (towers get 3–4 layers, spreads 2, compact 3, random ones must fit the footprint circle):
- Columns of discs stand on a square lattice 2p apart (p = centre distance of two crossed discs). Layer k sits p above layer k − 1. In each layer the column discs stand in one vertical plane and flat discs bridge neighbouring columns along it; the next layer turns 90°, its column discs crossing the ones below on vertical slit lines. A column disc needs a slit down, a slit up and one per bridge, at most three, which the five circle pieces cover.
- Assembly: each layer is a tree, built piece by piece on the bench, then lowered onto the layer below as one unit, every joint between the two sliding straight down together (the egg-crate method). The planner (`src/slots/plan.ts`) checks this independently: when no single piece comes out, it lifts off whole units above each height along an axis and plans each unit separately. The build animation shows a layer assembled raised above its place, then lowered.
- Round covers are the kit's disc, sized up from the piece size in steps (1, 1.25 … 2.5×), starting at the least size the brief asks for, until one rests level on the column tops with every support at least a tenth of its radius inside its edge, so it never rides on its rim. Fitted covers (`fittedCover`) are cut to the grid: the plan hull of its highest points grown by a quarter piece size with round corners (the hull's Minkowski sum with a disc), widened to the least size asked; a long grid gets a long top.
- Gates: the table stands at least 1.5 piece sizes tall with the cover on, spreads no more than twice the cover's width, keeps the cover's centre well inside its feet, and tips no sooner than 8°.
- Covers need the Circular kit: the angular kits' offset slits never close a braced loop. The gallery refuses a cover on any other kit.

**Braced joints** (`src/slots/hinges.ts`). Two crossed sheets touch only within a sheet thickness of their crossing line, so a slit joint is a hinge about that line. Crossings are found from the geometry (mid-planes meeting along a line inside both outlines). Each piece gets a twist (ω, v); a crossing allows relative rotation only about its line (5 equations), a floor contact does not slip (3 equations). The null space holds the mechanism modes. A mode that only turns pieces about vertical axes lowers nothing and is harmless. Any other mode is a failure if it moves the centre of mass (sags under its own weight) or a point the cover rests on (folds under a load on the cover). A tree of slit joints is always a mechanism; it takes the closed loops of a stacked grid, or the floor, to brace it. In the passing tables only the bridge flats can still turn a little on their own lines, which lowers nothing and carries nothing.

The cover sits on the highest upward hull face if, after clipping each piece's contact patch with that plane to the cover's bearing outline, the contacts surround the cover's centre by a margin. Checks: level cover, braced joints, and the usable surface: the share of the cover over its supports, where a load cannot tip it off, rated for the load that would tip the whole design.

**Describe it (Claude Opus 5.5).** Type a brief ("a tall lantern from cardboard discs, about 40 cm") and Claude writes a recipe: kit, form, whether it needs a top (`cover`), the top's shape (`round` or `fitted`) and least size across (`coverMm`, from sizes the brief names), piece count, piece size, sheet, pieces to favour or leave out, branching style, a title and a sentence on its choices. The page applies it and grows the gallery. Claude only chooses settings; the engine grows and checks every design, so a weak recipe gives fewer designs, never an unchecked one. `POST /api/kit-recipe` (`scripts/kit-recipe.ts`) calls `claude-opus-5-5` through `client.beta.messages.parse` with a Zod schema (structured output), adaptive thinking at medium effort, and server-side refusal fallbacks (`fallbacks: "default"`). It runs in the Vite dev server (`scripts/kit-recipe-plugin.ts`) and as a Vercel Function (`api/kit-recipe.ts`), with the same same-origin and `SITE_PASSWORD` checks as `/api/compare`; the key is read from `ANTHROPIC_API_KEY` (`.env.local` locally) and never reaches the browser. Recipes are clamped to the generator's limits (`src/slots/recipe.ts`).

**Designed by Opus** (`scripts/kit-agent.ts`, `src/slots/agent.ts`). In the other Claude mode Claude only picks settings and the engine grows at random, so a brief asking for symmetry cannot be guaranteed. Here Claude Opus 5.5 is an agent with two tools. `build_design` takes an exact spec, either a tree (pieces in build order, and for each piece after the first the slit it slides onto a slit of an earlier piece and which side it lands on, plus which as-built axis points up) or a stacked grid by its layout (column sites, layers, bridges per layer) with an optional round or fitted top, and returns the engine's report: what stops it building (an unknown or used slit, two pieces running into each other, a blocked slide), else every check, its size, and where each piece ended up with the way each free slit opens. Opus builds, reads the report, fixes, builds variations, and calls `present_designs` with 2 to 5 that pass every check. There is no fixed piece count (up to 80 per design). `POST /api/kit-agent` streams newline-delimited JSON (Opus's progress notes, each build's verdict, the chosen specs) to the page, which rebuilds each chosen spec in the browser with the same deterministic engine. It runs as a manual tool loop on `client.beta.messages.stream` with adaptive thinking at high effort, `display: "updates"` for the progress notes, eager input streaming with Zod validation of every tool input, prompt caching, and server-side refusal fallbacks; it stops after 30 turns or 270 s (the Vercel function allows 300 s) and then shows the last passing designs. A run typically takes 30 s to a few minutes. Same password and same-origin checks as the other endpoints.

**Kit sheet** (`src/slots/kitSheet.ts`, `src/slots/ui/KitSheetTab.tsx`). One laser sheet of loose kit pieces to build many designs from, set up on the page and downloaded as SVG, DXF and notes; `npm run kit-sheet` writes the same files to `out/kit-sheet/` from the command line. Full discs come in the proportions the generator uses, measured over 283 designs of every form, each form weighted equally (C2L 36%, C2I 34%, C3T 25%, C1 5% at 80 mm discs and 3 mm sheet; `npm run kit-sheet -- --measure` measures again), or any mix entered. Half discs, notched (H) or with one slit (H1), are set by count and cut in back-to-back pairs (in generated designs they are about 11% and 1% of the pieces, none in grids); plain discs (no slits) are extra too, as caps and spares; round tops are optional. Pieces sit in square cells one disc plus a gap wide. The sheet is outlines only unless Engrave labels is on, which engraves each piece's type and slit letters (so a design's build steps can be followed from the pile) and the fit strip's widths. A slit-fit strip with slits from sheet − 0.3 to sheet + 0.5 mm, widening left to right in 0.1 mm steps, goes in the band below the last row. Defaults: 24 × 18 in stock, 3 mm sheet, 80 mm discs, 26 slotted discs, 4 plain discs, 6 notched and 4 one-slit half discs, no tops, outlines only (40 pieces). The page warns when the stock is too small, when tops or half discs do not fit, and when the discs are too small for tables in that sheet.

**Form atlas** (`src/slots/atlas/`, `src/slots/ui/AtlasTab.tsx`, `npm run atlas`). Every kind of table the Circular kit makes within a piece budget, legal and not. Kit pieces sit on a cubic lattice: a joint puts two discs' centres p = 2R − 2ℓ apart along the slit line (41.6 mm at 80 mm discs), square to each other. H1 sits on it like a one-slit disc; an H sits with its notch line through a lattice point, and two H are never joined notch to notch. A table has a level surface on top (the top cut to fit, on three or more supports off a line) at least 1.5 piece sizes up, stands as built and tips only past 8°, nothing can drop out, no slit joint can swing (hinges.ts, the floor taken as non-slip), and at most 30 pieces. It must also be buildable: single pieces, or groups built on the bench and slid in together along one slit direction (how loops close; an egg crate's layers are such groups), found by a two-handed search, which is sound but not complete. The judge records every check a form fails, not just the first, and agrees with the gallery on all its cut-to-fit tables. Small forms are counted exhaustively (22, 116, 955, 10,363 and 138,608 forms of one to five pieces, about twelvefold per piece) and judged up to five pieces. Larger ones are mapped by MAP-Elites over loops of joints, height, plan, surface, symmetry and distance from an egg crate. A structure's fingerprint counts its joint motifs (Weisfeiler–Lehman, two rounds), and novelty is the mean fingerprint distance to the 15 most similar legal tables. By default, parents are seven times in ten the most novel of four legal tables, and grafts and prunes are on: that finds about twice the new structures, and several times the forms far from any egg crate, of choosing the most useful legal tables. `atlas-runs/novelty-ablation.md` has the runs. Runs go to `atlas-runs/<time>-<tag>/` (`atlas.json`, `summary.md`), not `results/`, because the comparison page bundles every JSON file there. The Form atlas tab maps a run by height against loops or distance from an egg crate, lists forms with thumbnails drawn from the lattice, and opens any of them in the gallery's design sheet: 3D build, checks (a near miss shows what it fails), parts, steps and laser files.

**Panel generator** is the prompt-driven tool described below.

`slots/index.html` (open `/slots/` on the dev server) turns a prompt such as "small tower", "round coffee table" or "sphere" into flat panels that slot together. Pick a slit type and the same prompt becomes a different construction:

| | Cross slit | Radial slit | Edge slit | Tab & slot | Pinwheel kit |
|---|---|---|---|---|---|
| Table | X or # base, top rests | star pedestal, top rests | ring of walls, top rests | blades or trestles tabbed through the top | closed ring of identical pieces, top rests |
| Tower | plus or # column | star column | log-cabin crib, can twist | stacked plates and walls, can twist | helix of identical pieces |
| Sphere | three perpendicular discs | meridian discs | not possible | not possible | not yet |

- Generators (`src/slots/generators.ts`) only place panels, give an assembly order with a straight insertion direction per panel, and declare which pairs join. They never draw slits.
- The carver (`src/slots/carve.ts`) cuts every slit from the insertion paths. A panel moving along m sweeps the convex hull of each piece and its translate; the part of that hull inside the other panel's slab, projected onto its plane, is removed. With the crossing line parallel to m this gives the half-lap, at any angle the slot width is (t₂ + t₁|cos θ|)/sin θ plus the fit clearance, and the three-disc sphere's relief slots fall out on their own. Only declared joints are cut, so anything else in the way is reported, not eaten.
- Panels are kept as exact convex partitions. Collision checking (`src/slots/collide.ts`) is the separating-axis test on convex prisms; a swept prism adds the axes e × m and m, so straight insertion paths are checked exactly.
- The planner (`src/slots/plan.ts`) ignores the generator's order and disassembles the finished object with swept tests: single parts first, then whole units above a height when single parts are stuck. Greedy removal is sound but not complete: "no sequence found" is not proof that none exists.
- Stability (`src/slots/stability.ts`): support polygon from ground contacts, centre of mass, tip angle; each part nudged in ~30 directions to label it locked, seated (gravity holds it), friction-held or loose. Translation only, rigid parts, no friction credited. Panel integrity: still one piece, and the thinnest bridge left (`src/slots/integrity.ts`). A narrow crossing counts as a bridge only if something substantial lies beyond it: the sharp point where a notch meets a curved rim, or where a slit wall meets the rim, is a tip, not a bridge (what lies beyond is under 8 neck-widths squared and under 5% of the piece), while a real neck between two parts of a piece, or a thin arm, still counts.
- The page searches six seeded candidates in a worker and shows the best that passes every check. It exports an SVG cut sheet at 1 unit = 1 mm (red cut, blue engrave) and the design as JSON. The prompt reader is rule-based like the generator's.
- Pinwheel kit (`src/slots/kit.ts`): identical regular polygons (triangle to decagon) with one slit per edge, all at the same offset and angle, as in a slot-together card kit. A fixed slit of width w fits pieces of thickness t meeting at θ only for θ ∈ [2·atan(t/(w−c)), 180° − 2·atan(t/(w−c))]; the tests confirm that range with the collision engine. Two interlocked pieces are related by a half-turn about the axis through the middle of their overlap, so a chain that alternates two slits is a product of half-turns: a screw motion, i.e. a helix (the tower). It closes into a flat ring of 2N pieces only when the two half-turn axes cross at 180°/N, solved by Newton's method (the table base). The page lists every ring the current kit closes and marks the ones whose pieces run into each other. Twisting the slits more than about 10° makes most rings collide, so the defaults use straight, off-centre slits. Closing a ring needs the last piece to flex, because its two slits lie on different lines; the check says so as a warning rather than claiming a rigid build order. Helices are filtered to stand within 30° of upright on their own convex hull, to be buildable by straight slides, and to have no end piece that gravity can pull out.
